inZKtagram

A feed you can check

The user chooses the ranking algorithm. A RISC Zero STARK proves the platform used that choice.

Juan Pose · paper: ZKML (EuroSys 2024) → verifiable recommendation

Problem

Recommendation is a promise

Platforms declare a ranking policy. DSA-style “pick a non-profiled feed” is still a declaration.

Without a proof, “we used Wellbeing” is unverifiable. The ZK proof is the product, not decoration.

Three algorithms · one crate

What the user can pick

1 · Engagement

Recency, virality, short bait, novelty from accounts you do not follow. The dopamine loop.

2 · Wellbeing

Followed accounts only, long-form, mostly chronological. No likes in the score.

3 · Mixed

60/40 blend, author-repetition cap. A compromise, still deterministic.

feed-core is compiled on the host and in the guest. Same function, same feed.

Statement

What is proved

Feed F is rank(A, params, candidates, now), and A is the algorithm in the user’s committed config.

  • Public (journal): algorithm id, hashes of config / params / candidates / feed, timestamp, image ID.
  • Witness: likes, follows, lengths, full candidate vectors — not in the journal.
  • Prover → verifier: server proves to the user or any auditor.
Why a zkVM

STARKs, not a Halo2 circuit

  • ZKML compiles TensorFlow → Halo2 SNARK. Great for ML ops; painful for sort / if / author caps.
  • RISC Zero lets us prove the real Rust ranker in a month, with a transparent setup.
  • Cost: receipts of hundreds of KB, prover in minutes on CPU. Verification stays milliseconds.
  • We measure that cost against native rank() and against ZKML’s DLRM/MNIST numbers.
Live demo

What to show

  1. Pick Wellbeing → long posts from followed accounts.
  2. Switch to Engagement → viral bait from accounts nobody follows.
  3. Verify → green. Browser recomputes feed_hash.
  4. Settings → malicious server → Verify fails: proved algorithm ≠ displayed feed.
  5. Download the receipt → verify.cmd (do not trust the UI’s STARK tick).
Trust model

Integrity, not input honesty

Proved

This execution of this image ID produced this journal. Illegal candidate lists (unsorted, duplicates, own posts) abort the guest.

Not proved

The candidate set is complete. The UI STARK check is a courtesy HTTP call. A transparency log of posts is out of scope.

Auditor: GET /api/audit/{id} → verifier-cli --candidates dump.json compares candidates_hash.

Evaluation

Tests and measurements

  • Completeness (CI): guest journal = native rank.
  • Application soundness (CI): illegal inputs abort; wrong algorithm / feed hash claims fail.
  • Cryptographic soundness: real STARK passed in 49 s; tampered journal and wrong image ID rejected.
  • N=50 Mixed: 96.7 s prove · 21 ms verify · 263 KB receipt · 16 µs native (~6 000×).

Full table: benchmarks/results.csv · Ryzen 7 2700X, Docker Linux.

Takeaway

Choice you can check

The interesting object is not a smarter ranker. It is a checkable binding between the algorithm the user picked and the feed they saw.

ZKML showed verifiable inference for committed models. inZKtagram shows verifiable ranking for a committed user choice.
